# 2147ea4 — Scaffold Phase 0: Medusa v2 + two-brand Next.js monorepo

Turned the uploaded `medusa-twenty-project` planning package (specs, TDD plans, AWS
infra script) into a working monorepo skeleton.

## What changed
- `apps/backend`: Medusa v2 backend, scaffolded via `create-medusa-app --skip-db`
  (Turborepo-based, `@medusajs/eslint-plugin`, Jest test scaffolding already in place).
- `apps/storefront-brand-a`, `apps/storefront-brand-b`: two independent copies of
  Medusa's official Next.js storefront starter, one per brand, on ports 8000/8001,
  each pointed at the same backend via a different (future) sales-channel publishable
  key. Package names scoped `@dtc/storefront-brand-a` / `-b` so Turborepo filters stay
  unambiguous.
- `docker-compose.yml` + `.env.example`: local dev stack — Postgres, Redis, backend,
  both storefronts, each storefront's Dockerfile building from the repo root so `npm ci`
  can see the whole npm workspace.
- `.github/workflows/ci.yml`: GitHub Actions CI (lint, backend unit tests, backend
  build), standing in for the GitLab+Jenkins pipeline `docs/specs/15-cicd.md` assumes,
  since this repo doesn't have that self-hosted infra.
- `docs/`, `infra/`: the full spec/TDD package from the upload, copied in as-is except
  two previously-empty specs — `18-folder-structure.md` and `19-milestones.md` — written
  up to describe the actual layout and Phase 0 completion status.
- `README.md`, `AGENTS.md`: rewritten for this project (the generated versions were
  generic Medusa-starter boilerplate).

## Bugs found and fixed while building this
- **Stale ESLint 8 nested under npm workspaces broke `next lint`** in both storefronts,
  with opaque errors (`Error while loading rule '@next/next/no-img-element': Cannot read
  properties of undefined (reading 'replace')`). Root cause: `@next/eslint-plugin-next`
  bundled with `next@15.3.9` assumes ESLint 9's `context.filename`, but the storefronts'
  own `package.json` still pinned `eslint@8.10.0` with a legacy `.eslintrc.js`. Fixed by
  moving both storefronts to ESLint 9 flat config (`eslint.config.mjs` +
  `next/core-web-vitals`) and doing a clean `node_modules` reinstall so only one eslint
  version was resolved workspace-wide.

## Verified
- `npm ci` (lockfile is consistent — this is exactly what CI runs).
- `npm run lint` — all three workspaces clean.
- `npm run build --workspace=@dtc/backend` — compiles.
- Full `npm run build` (all three) — backend succeeds; storefronts compile but fail at
  Next's "Collecting page data" step because a category page's static generation fetches
  from a live Medusa backend. Documented as a known Phase 0 limitation rather than
  worked around — CI builds only the backend for now.
