# f3a7e10 — Phase 2: conditional Stripe registration; document failed mocking attempts

## What changed
- `apps/backend/medusa-config.ts`: registers `@medusajs/payment-stripe` conditionally
  on `STRIPE_SECRET_KEY` being set. Registering it unconditionally throws at
  container-boot time ("Required option `apiKey` is missing in Stripe plugin") when no
  key is present — which is every environment available right now (this sandbox, and
  presumably CI until Vault is wired up). Comment in the file explains the resulting
  provider id is `pp_stripe_stripe`, not `pp_stripe` (Medusa builds it as
  `pp_<identifier>_<id>`).
- `docs/tdd/medusa-checkout-payments.tdd.md`: new "Mocking Stripe" section documenting
  two failed attempts at testing currency-correct payment session creation (TDD cases
  1-2), and why neither is worth chasing further in this environment.
- `docs/specs/19-milestones.md`: Phase 2 Stripe bullets split into what's actually done
  (conditional registration, verified) versus what's blocked (currency tests, full
  payment flow tests).

## Two mocking attempts, both dead ends — documented, not silently dropped
1. **`jest.mock("stripe")`** — has no effect. Traced the actual cause: Medusa loads
   payment providers through `@medusajs/utils/dist/common/dynamic-import.js`, its own
   dynamic-import mechanism, which doesn't route through Jest's require-based module
   registry. Confirmed by running it: with a fake `STRIPE_SECRET_KEY` and the mock in
   place, the real Stripe SDK still fired and got a real 401 from `api.stripe.com` —
   proof the mock was never in the loop.
2. **`nock` intercepting `https://api.stripe.com`** — installed `nock`, wrote an
   interceptor for `POST /v1/payment_intents`. In principle this should work regardless
   of how the SDK was loaded (nock patches Node's http/https layer directly). In
   practice: both test cases and the test suite's own shutdown hung to a 60+ second
   timeout. Root cause not chased down — an actively-hanging test is strictly worse
   than no test (it breaks CI with a slow, confusing failure), so it was removed rather
   than landed half-working. `nock` was installed and then uninstalled in the same
   round; `package-lock.json` is back to its prior state.

## Verified
- App boots and the full integration suite (10 tests, 3 files) still passes with
  `STRIPE_SECRET_KEY` unset — the conditional registration is a pure addition.
- `npm run lint` and `npm run build` on the backend — both clean.
