# 20d6941 — Phase 3: shared customer identity and partial-return restock tests

User picked "Phase 3: customers & returns" from a menu of build-direction options.
Covers `docs/specs/03-customer-model.md` and `docs/specs/06-returns.md`.

## What changed

### `apps/backend/integration-tests/http/customer-identity.spec.ts`
Covers TDD cases 1-4 from `medusa-customer-returns.tdd.md`:
- Register on Brand A (`POST /auth/customer/emailpass/register` → `POST
  /store/customers`), then log in on Brand B with the same credentials (`POST
  /auth/customer/emailpass`) — resolves to the same customer id, not a duplicate.
- The resulting JWT works identically presented against either brand's publishable
  key at `GET /store/customers/me` — confirms identity isn't channel-scoped, exactly
  as `03-customer-model.md` specifies (the publishable key scopes catalog/pricing
  context, not who you are).
- Placing one order per brand and then calling `GET /store/orders` returns both,
  each tagged with its own `sales_channel_id`.

**Real finding while writing this:** `medusaIntegrationTestRunner` restores the
database to the post-`beforeAll` snapshot before *every* `it` block, not just once
per file. A customer registered in one test doesn't exist in the next. The two
originally-separate test cases (identity portability, order history) had to be
merged into one `it`, since they're really one continuous customer journey and
splitting them meant the second block's login always failed with "Invalid email or
password."

### `apps/backend/integration-tests/http/returns.spec.ts`
Covers TDD case 6: an order for 3 units of one variant, 1 unit returned and
received, restocks the shared inventory pool by exactly 1 — not all 3, proving a
partial return doesn't over-restock.

**Two real findings while writing this:**
1. Medusa's return module rejects a return request that exceeds *fulfilled*
   quantity ("Cannot request to return more items than what was fulfilled") — an
   order that's merely paid/completed isn't returnable until its items are marked
   fulfilled. Added `POST /admin/orders/:id/fulfillments` before requesting the
   return, mirroring the real-world rule that you can't return something that
   hasn't shipped.
2. Admin users have no open self-registration endpoint — only an invite-accept
   flow. Rather than drive that full HTTP round trip in test setup, the test
   registers an auth identity the same way that flow starts
   (`POST /auth/user/emailpass/register`), decodes the actorless JWT it returns to
   get the `auth_identity_id`, and calls `createUserAccountWorkflow` directly to
   attach a `User` — the exact same workflow the real accept-invite route calls,
   without also needing a stored invite record.
