# f70f010 — Verify storefronts against a real seeded backend end to end

User picked "Wire up the storefronts" from a menu of build-direction options.

## What changed
- `docs/specs/19-milestones.md`: Phase 6 bullet updated from "not verified" to
  describing the real end-to-end run below.
- `README.md`: local-dev instructions corrected — they previously said to create a
  publishable API key per sales channel in the Admin, but `db:migrate` now seeds
  both keys automatically (since the Phase 1 seed script commit). The real step is
  reading the already-created keys out, not creating them.
- No application code changed. `.env.local` files for both storefronts were created
  locally with real (dev-only) publishable keys but are gitignored, not committed —
  their values are specific to whatever database seeded them.

## What was actually run
1. Reset the local dev Postgres to a clean state (it had accumulated duplicate data
   from the Phase 1 seed-duplication bug investigation) and ran `medusa db:migrate`
   fresh.
2. Started the Medusa backend (`medusa develop`) against it.
3. Pulled the real publishable keys and region IDs straight from the database and
   wrote them into `apps/storefront-brand-a/.env.local` and
   `apps/storefront-brand-b/.env.local`.
4. Started both storefronts and drove them with a headless Chromium. `chromium-cli`
   (this environment's usual browser-driving tool) wasn't installed, so used
   `playwright-core` directly against the pre-installed Chromium at
   `/opt/pw-browsers` instead — a reasonable substitute per the `run` skill's own
   documented fallback.

## Verified
- Both storefronts render the seeded "Cross-Brand Demo Tee" on their category page.
- The same cross-listed variant shows **$20.00 on Brand A** and **¥3,000 on Brand
  B** — exactly the per-currency prices the Phase 1 seed script set, each brand
  correctly resolving its own region.
- Selecting a size and clicking "Add to cart" completes successfully on both
  storefronts (`Cart (1)`), with zero console errors throughout.

## A red herring worth recording
The product detail page's CTA button reads "Out of stock" *before* any size is
selected — this looks like a bug at first glance, and cost real debugging time
(including a wrong hypothesis that the backend wasn't returning inventory data,
disproven by matching the storefront's exact query via `curl`). It's actually a
harmless copy quirk in the upstream `nextjs-starter-medusa` template: the button's
label logic checks `!selectedVariant && !options`, but `options` starts as `{}` (an
object, always truthy), so that branch can never fire — the button always falls
through to "Out of stock" until a valid variant is selected, and then correctly
flips to "Add to cart". Not something to fix in this repo (it's upstream template
behavior, not our code), but worth knowing before chasing it as a real bug again.

## Also fixed along the way
Ran into a Next.js `EADDRINUSE` + a stray `.next` directory removed out from under a
still-running dev server, which then 500'd. Fully killed all node processes bound to
the storefront ports before restarting cleanly — a reminder that `rm -rf .next`
while a dev server is running corrupts it rather than triggering a clean rebuild.
