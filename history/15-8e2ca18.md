# 8e2ca18 — Phase 3: tax configuration (JP consumption tax, US deferred)

Continuation of "continue building per specs"; picks up the last remaining Phase 3
bullet in `docs/specs/19-milestones.md`. Covers `docs/specs/01-medusa-config.md`'s
tax "Done means".

## What changed

### `apps/backend/src/migration-scripts/initial-data-seed.ts`
- Creates a 10% "Consumption Tax" rate (`JP_CONSUMPTION`) on the JP tax region via
  `createTaxRatesWorkflow`.
- Flips the JPY currency-level `PricePreference` to `is_tax_inclusive: true` —
  `createStoresWorkflow` already created a default (non-tax-inclusive) one for
  "jpy" when the store's `supported_currencies` was seeded, so this *updates* it
  rather than creating a new one (creating conflicts with "already exists").
- US intentionally gets a tax region (so `tp_system` has something to resolve
  against) but no rate — a single flat country-level rate would misrepresent
  state-varying US sales tax, and `01-medusa-config.md` marks the real
  provider/rate-table approach as still TBD.

### `apps/backend/integration-tests/http/tax.spec.ts` (new)
Two tests: a JP cart correctly computes 10% tax-inclusive tax, and a US cart
shows zero tax since no rate is configured for it yet.

**Real finding while writing this:** tax-inclusivity for a price is resolved from
whichever `PricePreference` matches how the price was actually *set* on the
variant. This test's (and the seed script's) prices are set as plain
`{amount, currency_code}`, with no region-specific price rule — so only a
**currency-level** preference (`{attribute: "currency_code", value: "jpy"}`)
takes effect. A region-level one (`{attribute: "region_id", value: <region id>}`)
was tried first and silently had zero effect on the cart's tax computation — no
error, the cart just came back non-tax-inclusive. Traced to `isTaxInclusive()` in
`@medusajs/pricing/dist/services/pricing-module.js`. The seed script's fix and this
test's fix are the same underlying mechanism, but the test needed one extra step:
since this test never runs `createStoresWorkflow`, no default "jpy" preference
exists yet, so it creates one from scratch via `createPricePreferencesWorkflow`
(whose input is a plain array, not `{ preferences: [...] }` — got a MikroORM
"required" error on the first attempt from wrapping it wrong) instead of updating
an existing one.
