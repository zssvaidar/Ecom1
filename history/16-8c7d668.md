## What changed

### `apps/backend/integration-tests/http/shared-inventory.spec.ts`
Added two more products to the shared setup — an "Out Of Stock Tee" (stock 0) and
a "Last Unit Tee" (stock 1) — plus a second publishable key for Brand B (the file
previously only had one), and three new `it` blocks:

- **Case 5** — posting an add-to-cart request for the zero-stock variant is
  rejected with a 400, and the inventory level stays at `0/0` (stocked/reserved)
  rather than going negative.
- **Case 6** — an Admin-side restock via
  `inventoryModuleService.updateInventoryLevels` is immediately visible to both
  brands' `/store/products` responses, with no brand-specific step needed —
  confirms the shared item isn't cached or scoped per channel.
- **Case 7** — built a `buildCompletableCart` helper that drives a cart through
  address/shipping-method/payment-session, stopping just short of `/complete`, then
  fired two such carts' `/complete` calls simultaneously via `Promise.allSettled`
  against the shared last-unit item — one via Brand A, one via Brand B.

**Two real findings while writing this:**
1. `inventoryModuleService.updateInventoryLevels()` takes `{inventory_item_id,
   location_id, stocked_quantity}`, not `{id, stocked_quantity}` — passing the
   inventory_level row's own `id` throws "Item undefined is not stocked at
   location undefined" since the service reads item/location off the input, not
   off the row id.
2. Fetching a variant's live stock via the Store API needs the field spelled out
   explicitly — `fields=variants.id,variants.inventory_quantity` — rather than the
   `*variants.inventory_quantity` wildcard form used for relations elsewhere in
   this codebase (catalog-channels.spec.ts uses `*variants.calculated_price`
   successfully); the wildcard silently returns the variant without the field at
   all rather than erroring, so this looked at first like the restock hadn't taken
   effect.

**The actual result for case 7 is the interesting one:** no new locking code was
needed. Medusa's reservation system already prevents the oversell — exactly one
of the two simultaneous completions resolves with `type: "order"`, the other fails
with "Not enough stock available", and the final available quantity
(`stocked_quantity - reserved_quantity`) lands at exactly 0, never negative. This
commit is pure verification of existing behavior, not new application code.
