## What changed

### `apps/backend/src/subscribers/low-stock-alert.ts` (new)
An opt-in low-stock alert: an inventory item is only watched once its
`inventory_item.metadata` carries a `low_stock_threshold` — Medusa v2's inventory
module has no such concept built in, so this is entirely custom. The "already
alerted" state lives in that same metadata (`low_stock_alerted`), since
`inventory_level` has no metadata field of its own (only `inventory_item` does —
confirmed against the Admin API's `AdminUpdateInventoryLocationLevel` validator,
which only accepts `stocked_quantity`/`incoming_quantity`).

**The real finding here is architectural, not a bug fix:** a sale only *reserves*
stock at checkout. `reserveInventoryStep` calls
`InventoryModuleService.createReservationItems_()`, which updates the
`inventory_level` row's `reserved_quantity` through the repository directly
rather than through the module's own decorated `updateInventoryLevels()` method —
so **no inventory-level-updated event fires at order-placement time at all**,
module-level or workflow-level. `stocked_quantity`, and the events tied to it,
only change later at fulfillment. The correct hook for "a sale dropped available
stock" is `ReservationItemWorkflowEvents.CREATED` (`reservation-item.created`),
which core-flows' `completeCartWorkflow` emits explicitly (with `{id, order_id}`)
for exactly this reason. Restocking is a separate path: the Admin location-level
update route runs `updateInventoryLevelsWorkflow`, which *does* emit
`InventoryLevelWorkflowEvents.UPDATED`. So the subscriber listens for both events
— the first to detect a downward crossing, the second to clear the alerted flag
once stock recovers above the threshold — branching on `event.name` since the two
payloads carry different id semantics (a reservation id vs. an inventory level
id).

Lint caught a related, smaller finding along the way:
`@medusajs/prefer-workflow-event-over-module-event` flagged an earlier draft that
subscribed to the raw module event `InventoryEvents.INVENTORY_LEVEL_UPDATED`
instead of the workflow-level `InventoryLevelWorkflowEvents.UPDATED` — the fix
surfaced the deeper finding above, since switching to the workflow event broke a
test that had been triggering "sales" via direct
`inventoryModuleService.updateInventoryLevels()` calls, which (correctly) don't
touch that event at all.

### `apps/backend/integration-tests/http/shared-inventory.spec.ts`
New `it` block covering case 9, added a fourth product ("Low Stock Tee") to the
shared fixture set. Drives the scenario through **real checkouts** (using the
existing `buildCompletableCart` helper from the case-7 concurrency test) — one
sale via Brand A crossing the threshold, one via Brand B that shouldn't re-alert
— and a **real restock** via `updateInventoryLevelsWorkflow` (the same workflow
the Admin API's location-level route runs), not direct module calls, since that's
what the subscriber actually listens to in production. An earlier draft poked
`stocked_quantity` directly and passed for the wrong reason (it exercised a
different, module-level event than what real sales trigger) — the final version
would have caught that gap immediately, since a direct module call never creates
a reservation.

### `docs/specs/19-milestones.md`
Phase 1's shared-inventory bullet gets the case 9 writeup above, plus a corrected
note on case 8: it doesn't map onto Medusa v2's actual architecture at all, not
just "needs a test harness for a short TTL" as previously written —
`CreateReservationItemInput`/`UpdateReservationItemInput` carry no expiry concept
whatsoever, so there's no reservation TTL to configure short for test speed.
Building one would mean designing custom expiry logic Medusa doesn't have, which
is a different, larger task than verifying existing behavior — out of scope for
what this TDD case was asking to check.
