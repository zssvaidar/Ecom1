# 5e1077b — Phase 4/5: Twenty CRM sync integration (outbound + inbound webhooks)

User picked "Twenty CRM (Phase 4/5)" from the remaining backlog. Covers
`docs/specs/07-twenty-data-model.md` and `docs/specs/08-integration-webhooks.md`.

## The scoping problem, up front

Twenty CRM cannot actually run in this environment: `dockerd` fails to start
under this sandbox's restricted privileges (confirmed — `ulimit: error setting
limit (Operation not permitted)`, then no docker socket), and there's no Twenty
Cloud account/API token available either. Both self-hosting and Cloud were
therefore off the table for real end-to-end verification. Rather than guess at
either, the work split into what's actually buildable and testable in this repo
(the Medusa side of the contract, Phase 5) versus what can only be configured
inside a real running Twenty workspace (the object model, Phase 4) — the latter
became a runbook, not code.

## What changed

### Phase 5 — Medusa ↔ Twenty integration (built and tested)

**`apps/backend/src/modules/twenty-sync/`** (new custom module):
- `models/twenty-sync-event.ts` — a Postgres-backed audit/idempotency log
  (`idempotency_key` unique, `status`: pending/delivered/dead, `attempts`,
  `last_error`, `first_attempted_at`/`delivered_at`). Redis+BullMQ owns retry
  *timing*; this table is the source of truth for "has this order already been
  synced" and "which events are dead" — a Redis flush can't silently reopen an
  idempotency guarantee if the durable state lives in Postgres instead.
- `signature.ts` — shared HMAC-SHA256 sign/verify (timing-safe compare), used
  by both directions.
- `queue.ts` — a real BullMQ `Queue`/`Worker` pair. Custom backoff strategy
  matching the spec's exact schedule (1m, 5m, 30m, 2h, then hourly); a job that
  keeps failing past 24h elapsed (tracked via `first_attempted_at`, not
  BullMQ's own attempt counter) gets marked `dead` in Postgres and emits a
  `twenty-sync.dead` event (logged as an alert) — the worker returns rather
  than throws at that point, so BullMQ stops retrying and Postgres's `dead`
  status is authoritative.

**`src/subscribers/twenty-order-sync.ts`** — on `order.placed`, builds the
exact payload shape from `08-integration-webhooks.md` (customer, line items,
address, currency, total, `sales_channel` from the order's own channel name)
and hands it to the queue. Wrapped in try/catch so a Twenty-sync problem can
never affect the order — an explicit, testable version of the guarantee Medusa's
event bus already provides implicitly by catching subscriber errors on its own.

**`src/api/webhooks/twenty/fulfillment/route.ts`** + **`src/api/middlewares.ts`**
— the inbound receiver. Needs the exact raw request bytes to verify its HMAC
signature against (re-serializing the parsed JSON body could produce different
bytes than what was actually signed), so `middlewares.ts` turns on
`preserveRawBody` for this one route. No configured secret means requests can
never be verified, so that fails closed (401) rather than accepting unsigned
requests. The write-back scope guard from `00-architecture.md` is implemented
as an **allowlist** (only `fulfillment_status`/`tracking_number`/`carrier` are
ever read from the body) rather than a blocklist — there's no way for `total`,
`payment_status`, or `status` to reach a real order field through this route
regardless of what's in the payload, because nothing ever reads those keys.

**`src/workflows/apply-twenty-fulfillment-update.ts`** — the actual order
mutation, extracted into a proper workflow after `medusa lint` flagged the
route handler mutating the order module directly
(`@medusajs/no-service-mutations-in-api-route`, a real rule catching a real
AGENTS.md violation: "business logic belongs in workflows, not route
handlers"). Applies idempotently by upserting into
`order.metadata.twenty_fulfillment` — redelivery just overwrites the same
values, never a duplicate or an error, and unknown `medusa_order_id` surfaces
as the workflow's own `MedusaError` NOT_FOUND, which the route turns into a
404.

**`apps/backend/integration-tests/http/twenty-webhooks.spec.ts`** (10 tests) —
a plain Node `http.createServer` stands in for Twenty's receiver (this
project's own TDD doc calls for exactly that fixture: "a mocked Twenty
endpoint that can be toggled reachable/unreachable"). Covers: the outbound
payload shape and successful delivery, matched against the raw bytes the mock
actually received; an order completing normally when the mock is set to fail
(the "Twenty down never blocks checkout" guarantee); the inbound signature
cases (missing header, wrong secret, tampered body — all 401); the write-back
allowlist actually excluding injected fields; redelivered updates being a
no-op; and an unknown order id returning 404. The 24h dead-letter transition is
driven directly through `processJob` (exported for exactly this) with a
manipulated `first_attempted_at` 25 hours in the past — the equivalent of the
"fake clock to fast-forward through the backoff schedule" fixture the TDD doc
asks for, since actually waiting 24 hours in a test isn't practical. The
backoff schedule's *values* are separately unit-tested as a pure function in
`src/modules/twenty-sync/__tests__/queue.unit.spec.ts`.

**Real finding while building this:** `bullmq`/`ioredis` were already sitting
in `node_modules` as transitive dependencies of Medusa's own
`@medusajs/event-bus-redis`/`@medusajs/workflow-engine-redis` packages (neither
of which this repo registers — both still run in-memory today). Relying on
that undeclared transitive availability would be fragile, so `bullmq` was
added as an explicit direct dependency instead.

### Phase 4 — Twenty CRM data model (runbook, not code)

`docs/specs/07-twenty-data-model.md` gained an "Implementation status" section
spelling out exactly what to configure by hand inside a real Twenty workspace:
the Person "Brands purchased from" multi-select field, and the
Shipment/Fulfillment Task custom object with all the fields from that doc's own
table. It also names a real open question this repo can't resolve without a
live instance: whether the target Twenty version can turn an inbound webhook
into record upserts directly (a webhook-triggered Workflow) or whether a sync
process needs to call Twenty's own GraphQL/REST API instead — Twenty doesn't
ship a generic "POST arbitrary JSON, upsert records" endpoint out of the box,
and which mechanism actually exists depends on the Twenty version in use.

`docker-compose.yml` gained a self-hosted `twenty`/`twenty-db` service pair
behind an opt-in `twenty` compose profile — `docker compose --profile twenty up`
— explicitly flagged as a best-effort starting point against Twenty's
self-hosting docs, not a verified-working config (can't be booted here, no
Docker daemon). `docker compose config` (which needs no daemon) did catch one
real bug before it shipped: a required (`:?`) `TWENTY_APP_SECRET` var would
have broken `docker compose up` for *everyone*, not just people using the
`twenty` profile, since compose interpolates every service's env block
up front regardless of which profile is active — switched to a placeholder
default with a comment explaining why.

## Verified
- `twenty-webhooks.spec.ts`: 10/10 passing.
- Full integration suite: 7 spec files, 28 tests, all passing together.
- Unit suite (first real one in this repo — previously nothing existed under
  `src/**/__tests__`, so CI's `--passWithNoTests` flag is now removed):
  `signature.unit.spec.ts` (5 tests) + `queue.unit.spec.ts` (3 tests).
- `npm run lint`: 0 errors, 1 pre-existing unrelated warning. Two real findings
  fixed along the way — the route-handler mutation above, and a generic
  `throw new Error` in the queue worker that `@medusajs/use-medusa-error-not-
  generic-error` flagged, switched to `MedusaError`.
- `npm run build`: clean.
- **Outside the Jest harness:** ran the module's own migration against the
  real dev Postgres (confirmed the `twenty_sync_event` table and its
  constraints); started a real `medusa develop` server against a real Redis
  and a real standalone Node mock server (not the test harness's mock), placed
  a real order via curl, and confirmed the exact same payload/signature
  arrived at the mock and the audit row reached `delivered`; then sent a real
  signed curl request to the inbound route with an injected `total: 999999`
  field and confirmed the order's metadata updated correctly while the
  injected field was silently dropped.
- `docker compose config` / `docker compose --profile twenty config --services`
  confirm the profile gating itself works, independent of whether Twenty's
  image/env vars are exactly right.

## CI changes
Added a `redis:7` service container to `test-backend-integration` (only
`twenty-webhooks.spec.ts` uses it — every other spec file runs with
`TWENTY_WEBHOOK_URL` unset, so their `order.placed` events never touch Redis).
Removed the now-stale `--passWithNoTests` flag from the unit-test CI step now
that real unit tests exist.
